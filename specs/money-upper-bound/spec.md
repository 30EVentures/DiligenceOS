# Money upper bound: 2^53 - 1

## Goal

`Money(2**64, "USD")` was valid, and no int64 system can hold that. The owner chose
the bound on 2026-10-12: **`amount_minor` must be at most 2^53 - 1
(9,007,199,254,740,991)**, the largest integer every JSON implementation reads
exactly. Canonical JSON then means the same thing in Python, JS and Go.

## Included

- `types.py`: `MAX_AMOUNT_MINOR = 2**53 - 1`; `Money` refuses anything larger
  (a `ValueError`, like every other bad amount, so every existing caller that
  turns a `ValueError` into a refusal keeps working).
- `api.py`: the machine-readable description of `transaction.amount_minor` states
  the bound.
- Conformance corpus: the three cases marked `known_failure` for this decision
  (`mf-money-beyond-int64`, `mf-money-astronomical`,
  `mf-request-transaction-beyond-int64`) lose the marker and must now be refused.
  Added: 2^53 is refused (one past the bound); the policy cap is held to the same
  bound. The corpus is regenerated by `conformance/build_diligenceos_1.py`, not
  edited by hand.

## Not included

- No change to receipt, delegation, auth or log formats. A receipt already issued
  with an amount above the bound (none exist outside tests) now fails
  verification as malformed money.
- Cumulative spend is a sum of amounts each at most the bound and held at or below
  a policy cap that is itself at most the bound; Python ints do not overflow, so no
  second check is added.
